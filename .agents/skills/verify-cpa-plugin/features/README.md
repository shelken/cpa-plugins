# 插件验证地图

本目录是 cpa-plugins 里插件验证的维护源。驱动任何插件前先读本文件，再进对应特性文件照做。

## 基线前提

- 沙箱由 `go run scripts/dev-sandbox.go -plugin <id>` 启动，端口默认 `18317`，目录 `~/.cache/cpa-plugins/sandbox/<id>/`。
- 每次运行开始时会清空沙箱目录，因此每一轮都从干净状态起步。
- 管理面密钥从 `~/.cache/cpa-plugins/sandbox/<id>/management-key` 读。`config.yaml` 里的 `secret-key` 在宿主启动后已是 bcrypt 哈希，不可用。
- 需要管理面留活就用 `-keep`；不用就让它自己收尾。
- 沙箱不需要凭据。凭据档需要用户现场扫码，见 `auth-login.md`。

## 驱动约定

- 每条命令都当作字面量执行，路径、id、state 原样传递。
- 命令全部以 `cd <插件仓>` 为起点，管理面请求用 `go run scripts/management-api.go -sandbox <id> -path <管理面路径>` 打到沙箱宿主，密钥由脚本读。
- 沙箱不配 `api-keys`，所以沙箱里的 `/v1/models`、`/v1/chat/completions` 不带任何头即可；真实部署上 `/v1` 要客户端 API key，与管理密钥不是一回事。
- 每条断言都由"命令 + 预期可观测结果"成对给出。结果不符就是没通过，不要换个说法让它通过。
- 只管自己启动的实例；端口只有一个，别并行驱动同一宿主。

## 取证与跳过报告

- 证据是命令原文加真实输出：真机档留断言行与 `host.log`，管理面档留响应体，产物档留校验行。
- 单元测试不算生产端证据。
- 依赖凭据的链路必须同时记录账号状态。账号未验证时的失败不得定性为插件缺陷。
- 某条入口没跑到就报"未跑到"并给出缺的前置条件，不要用别的入口冒充。
- 证据拷到 `~/.cache/cpa-plugins/evidence/<plugin>/<日期>-<特性>/` 后再收尾。

## 特性条目契约

每个特性文件以 H1 标题和一段用户视角的行为描述开始，随后固定四个 H2，顺序不变。

1. `Sub-features` 用短 id 逐条列行为。
2. `How to get to it (user POV)` 列全部用户入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用成对条目给出用户动作、确切命令与可观测结果。
4. `Gotchas` 列会浪费或作废一轮验证的坑。

地图只写用户路径、稳定入口、所需状态、命令与可观测证据，不写实现细节。

## 特性

- [模型清单](./models.md) 覆盖模型报送、黑名单过滤与静态清单一致性。
- [扫码登录](./auth-login.md) 覆盖登录入口、轮询、凭据归属与离线归属判定。
- [对话](./chat.md) 覆盖流式增量、非流式聚合与请求保真。
- [额度](./quota.md) 覆盖额度能力声明、实时拉取与剩余比例换算。
- [打包与安装](./release-install.md) 覆盖清单不变量、包结构自检与安装态校验。

`echo-probe` 没有独立条目。它是探针插件，验证它等于验证离线档加真机档本身。
