# 插件版本与发布全链路由脚本生成

升一次版本要人手改 `plugin.json` 的 `version`、三处产物地址、推标签、再回填哈希，其中只有哈希有脚本兜底，地址漏改要到用户装不上才发现。因此这条链路整体交给脚本，人只写变更集，工具按 `scripts/` 现有风格自建。

## Status

accepted

## Considered Options

- 维持现状，靠人同步版本号与三处地址：流程最短，但没有任何机制强制「改了插件就得留下版本意图」，改动可以一路合入而不体现在版本上
- 引入 changie：Go 原生，但发布聚合与打标签仍要按本仓约定裁剪，多一层外部依赖再加一层胶水
- 引入 `@changesets/cli`：生态成熟，代价是给纯 Go 仓库引入 Node 工具链

## Consequences

- `plugin.json` 的 `version`、`install.artifacts[].url` 与插件 Go 代码里的版本字面量都变成产物，不再手工编辑，变更集是唯一入口
- `release.go record` 仍然必要：哈希只能由真实上传的产物得出，本地构建不可复现
- 发布不再由人推标签触发改动内容：合并含变更集的提交后运行 `release.go version` 产出新版本与三处地址，打标签这一步只搬运用脚本产出的版本
- CI 增加一条门禁：改动了 `plugins/<id>/` 却没有留下版本意图时失败；留下意图有两种形式，一是变更集文件进了历史，二是 `plugin.json` 的版本已经变过（变更集在提交前就被 `version` 子命令消费掉的流程）
- 标签命名定为 `<plugin-id>/v<version>`，每个插件独立版本、独立发布
- 构建完成后由工作流下载自己的产物回填哈希并重建 `registry.json`，宿主读到的新版本总是带真实哈希
