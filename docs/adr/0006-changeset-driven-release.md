# 插件版本与发布改由变更集驱动

现状是版本号写在 `plugin.json` 里手工维护，发布靠手工推 `<plugin-id>/v<version>` 标签，构建完成后还要手工把真实哈希回填进清单。这条链路上有三处人工动作，且没有任何机制强制「改了插件就得留下版本意图」，改动可以一路合入而不体现在版本上。因此后续所有插件的版本控制与发布统一改由变更集（changeset）驱动：每次影响插件的改动提交一个声明意图的变更集文件，累积后由发布环节消费，决定升哪个插件的哪个版本、生成变更日志并发起发布。

## Status

accepted

## Considered Options

- 维持手工打标签：流程最短，但没有版本意图的载体，漏发与版本跳号都无人拦。
- 引入 `@changesets/cli`：生态成熟、语义现成，代价是给纯 Go 仓库引入 Node 工具链。
- 引入 Go 原生的变更集工具（如 changie）：与现有 Go 工具链一致，发布聚合与打标签需要自建。

具体实现选型留待设计时定，本记录只锁定「由变更集驱动」这一方向。

## Consequences

- `plugin.json` 的版本号变成产物而非源头，不再手工编辑；变更集是唯一入口。
- `scripts/release.go` 的 `record` 仍然必要：哈希只能由真实上传的产物得出，本地构建不可复现，这一步不会被变更集取代。
- 发布工作流的触发方式要从「推送标签」改成「合并发布提交后打标签」，`release-plugin.yml` 与 `README.md` 的「发布流程」两节需要重写。
- CI 增加一条门禁：改动了 `plugins/<id>/` 却没有对应变更集时失败。这条门禁是本次方向的核心价值所在。
- 每个插件独立版本、独立发布的约定不变；`<plugin-id>/v<version>` 这类标签命名在实现选型确定后一并定稿。
