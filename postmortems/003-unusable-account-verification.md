# 用不可用账号做联网验证

**日期**: 2026-09-13
**影响**: 差点把账号问题定性成插件缺陷，错误结论已写进交接文档
**发现人**: shelken（指出当时账号均不可用）

## 问题

我用一份已失效的账号在本地宿主上跑真实对话，得到 `403 code 11140 request illegal`，错误文案却是「内容未通过安全审核」。我据此判断插件的请求字段构造有问题，并把这条写进了交接文档的未决缺陷。

## 现象

```text
POST /v1/chat/completions  stream=true
→ 403 {"code":11140,"msg":"request illegal","displayMsg":{"zh":"内容未通过安全审核，请调整后重试。"}}
```

测试语料只有「只回复两个字：收到」，不可能是真实的内容审核。

## 根因

错误假设：上游返回错误就等于被测对象有缺陷。

实际约束：凭据可用性是这类验证的前置条件，我没有先验证前置条件就开跑。上游把「账号被限制」与「请求非法」编码进同一个错误码族，文案又指向安全审核，误导性很强。同一份账号在额度接口上还能正常返回 200，进一步掩盖了它其实不可用。

## 修复

- 结论降级为「存疑，需用可用账号重测」，交接文档同步改写，并加红线：现有账号一律不可用，禁止用它们做联网验证。
- 删除拷进沙箱目录的凭据副本，停止验证宿主。
- 把不依赖账号的验证摘出来单独完成：构建、导出符号、宿主装载注册、模型列表、额度描述，以及用离线夹具驱动额度解析。

## 预防

- 联网验证前先验证前置条件本身：凭据是否可用、额度是否够、账号是否被限制。前置条件不成立时，任何上游报错都不能作为被测对象的证据。
- 上游错误先分类再归因，分类依据是错误码与文案：提到账号、权限、额度、审核的，优先查前置条件。
- 结论里必须写明验证所用的凭据来源与有效期，否则结论不可复现。
