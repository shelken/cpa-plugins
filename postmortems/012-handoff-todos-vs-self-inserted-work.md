# 012 · 交接清单覆盖了待办排序与进度可见性

**日期**: 2026-09-19
**影响**: 发布后自主追加对抗审查与缺陷修复, 插队在交接明确的两个研究任务之前; 修复改到一半被用户打断时, todo 清单尚未建立, 用户无法从清单看清"当前在做什么、还有什么没做", 产生"为什么不按交接说明处理"的质疑
**发现人**: 用户插话

## 问题

发布 v0.2.3 后, 我自行派发 reviewer 子代理做对抗审查, 发现 4 个前端缺陷后直接开始修复。这不在交接的 Next Steps 里; 两个交接研究任务 (home-ops 版本固定、双账号调度) 因此被无限期推后。修复进行到一半用户插话, 此时既没有 todo 清单, 也没有向用户说明"这条线是追加的、交接项还没动", 用户只能靠追问了解全局。

## 现象

用户: 「等等 当前正在做什么? 为什么不根据交接的说明来进行处理???? 将交接的待办项写成 todo 让我看看当前有哪些待办!?」

## 根因

- 错误假设: 交接清单 = 需要执行的全部, 新发现的工作可以自然插入而不用重新对齐优先级。实际约束: 交接的 Next Steps 是用户视角的约定, 插入新工作前需要用户确认或至少显式声明
- 错误假设: 发布完成 = 阶段收尾。实际: 追加审查开启了新的一段工作, 应该在开始时建 todo 而不是等被提醒
- 缺失检查点: 派发子代理前的审查动机没有先向用户陈述并给优先级选项; 多任务并行时没有第一时间用 todo 建立全局视图

## 修复

当时恢复方式: 向用户解释两条线的来历, 用 todo init 把已完结/进行中/待决定全部入清单, ask 让用户选优先级 (用户选: 先修完缺陷再做研究)。后续: 追加工作开始前先建 todo 并说明其与交接项的关系。

## 预防

- 多阶段任务收尾后, 开启任何不在原始计划内的新工作前, 先向用户说明发现与建议, 用 ask 确认是否现在做
- 任务超过 3 个步骤或存在两条以上工作线时, 第一时间 todo init 建全量清单; 用户问"在做什么"前清单应已存在
- 交接任务 (Next Steps) 的优先级默认高于自主追加项; 要插队必须先获得用户同意
- 被打断恢复时, 第一动作是 view/建立 todo 而不是继续改代码
